# M4A (AAC) episode support

Date: 2026-09-20
Status: planning — not started
Companion to: `news-radar/docs/plans/2026-09-20-m4a-switch.md` (the master
plan — why, size math, rollout order, verification list)

## Context

The techradar feeds (AI + Robotics) are moving new episodes from `.mp3` to
`.m4a` (AAC, 32 kbps mono) to get the GitHub Pages site under its 1 GB limit.
Old episodes stay `.mp3` and are **not** re-encoded, so feeds will serve a
mixed catalog for ~2–3 months and the app must handle both indefinitely.

This app must ship its changes **before** the first m4a episode is published.

## Why old episodes are not re-encoded (constraint this app imposes)

`EpisodeEntity.audioUrl` is the Room primary key, and chapters, deep-dives,
downloads, positions, heard and liked state all hang off it. A URL change from
`…-2026-09-01.mp3` to `…-2026-09-01.m4a` would look like a brand-new episode:
duplicates in the list and all per-episode state orphaned. Nothing to build
here — just don't let anyone "helpfully" re-encode the back catalog without
first adding a stable episode identity (e.g. key on `<guid>` with a
migration). That is out of scope for this change.

## Required change

### Cast MIME type — `service/PlaybackService.kt:322-326`

When switching to `CastPlayer`, a `MediaItem` with no MIME type gets
`setMimeType("audio/mpeg")` hardcoded. A Cast receiver told an MP4 container
is `audio/mpeg` may refuse to load it.

Derive it from the URL instead:

| Extension | MIME |
|---|---|
| `.mp3` | `audio/mpeg` |
| `.m4a`, `.mp4`, `.aac` | `audio/mp4` (`.aac` raw ADTS: `audio/aac`) |
| `.ogg`, `.opus` | `audio/ogg` |
| anything else | `audio/mpeg` (today's behaviour) |

Strip `?query` and `#fragment` before taking the extension, the same way
`CacheStorage.ext()` already does (`data/storage/CacheStorage.kt:40`) — extract
that into a shared helper rather than writing a second copy.

This closes the existing backlog item "Handle non-MP3 mimeTypes for Cast".

Better long-term: persist the RSS `<enclosure type="…">` on `EpisodeEntity`
and set it on every `MediaItem` (`Episode.toMediaItem`, line 357, currently
sets none). That needs a DB migration, and `RssParser` (line 59) currently
reads only the enclosure `url`. Not needed for this change — extension
sniffing is sufficient for our own feeds.

## Already fine — verified by reading the code, confirm by testing

- **Local playback / streaming / downloads:** ExoPlayer sniffs the container;
  no MIME needed. `DownloadWorker` is format-agnostic.
- **Download filename:** `CacheStorage.ext()` takes the extension from the
  URL (falls back to `mp3` only when there is none).
- **Deep-dive sidecar JSON:** `DeepDiveOrchestrator.kt:96` already rewrites
  `\.(mp3|m4a|ogg)$` → `.json`.
- **Chapters:** the app reads only the Podcasting 2.0 JSON via
  `<podcast:chapters>` (`ChapterRepository`); there is no ID3 parsing, so the
  loss of ID3 chapters in m4a files does not affect it.
- **RSS parsing:** enclosure `type` is ignored, so `audio/x-m4a` is harmless.
- **Seeking:** news-radar will write m4a with `+faststart` (moov atom first),
  so streaming seek works without downloading the whole file.

## Related fixes — independent of m4a, surfaced by the same review

The techradar site now purges audio artifacts after 90 days and whole
episodes after 150. The app never removes episodes that have dropped out of
a feed (`upsertFromFeed` only inserts/updates), so old rows now point at
URLs that 404.

1. **Uncaught exception on chapter fetch — likely crash.**
   `FeedApi.fetchChapters` throws on any non-2xx. All three callers run in a
   bare `launch` with no try/catch and no `CoroutineExceptionHandler`:
   `ui/player/PlayerViewModel.kt:257`, `:345`, and
   `playback/PlaybackController.kt:101`. Opening a never-before-played episode
   whose `.chapters.json` has been purged (or hitting any transient network
   error) will throw out of the coroutine. In `PlayerViewModel` it also
   prevents the `chaptersForEpisode(...).collect` that follows from starting.
   Fix: `runCatching { … }.onFailure { Log.w(…) }` around each fetch.
   **Do this first, regardless of the m4a timeline.**
2. **No playback error surface.** There is no `onPlayerError` handler
   anywhere; a 404 audio URL just silently doesn't play. Show a snackbar
   ("Episode audio is no longer available").
3. **Optional:** on feed refresh, flag or hide episodes older than the feed's
   oldest item whose audio is not downloaded, instead of listing dead entries
   forever.
